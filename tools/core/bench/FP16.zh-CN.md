# SymQG 的 FP32/FP16 配置与存储

这条路径接受 FP32 输入和查询，将数据库向量存为 FP16。查询、路由计算、SymQG 编码和最终精排使用 FP32；不会在索引加载时复制一份完整的 FP32 数据库。原有 FP32 配置继续可用。

## 统一的精度配置

FP32 与 FP16 共用 QuantizedGraph 搜索、入口路由和索引 dump/load，存储精度可显式选择，不按数据集名称分流：

| 配置位置 | FP32 存储 | FP16 存储 |
|---|---|---|
| local_builder 的 `BuilderClass` | `HnswStreamer` | `HnswStreamer` |
| local_builder 的 `QuantizerName` | `Fp32Quantizer` | `Fp16Quantizer` |
| 检索 `IndexConfig.data_type` | `DT_FP32` | `DT_FP32` |
| 检索 `IndexConfig.quantizer_param.type` | `kNone`（也可省略） | `kFP16` |
| `use_quantized_graph` | `true` | `true` |
| 查询与精排计算 | FP32 | FP32 |

显式构建示例中，只需在 `BuilderCommon` 选择对应的 `QuantizerName`，并指定新的工作/快照路径；不能同时设置 `ConverterName`。例如 FP32 检索配置为：

```json
{"index_type":"kHNSW","data_type":"DT_FP32","metric_type":"kCosine",
 "dimension":768,"use_quantized_graph":true,"quantizer_param":{"type":"kNone"}}
```

改成 `"type":"kFP16"` 就是 FP16 存储的检索配置，但必须打开对应精度构建的索引。这不是在查询时转换已有索引。

旧 FP32 构建方式仍兼容：Cohere 的 `CosineFp32Converter` 和 GIST 的原始 FP32 输入无需迁移。本目录原 FP32 性能配置继续保留；新增的显式 `Fp32Quantizer` 构建入口经过小规模端到端验证，不把重建的新图直接等同于历史百万快照。

已有数据集配置保留各自已测的搜索参数：

| 数据集 / 存储 | 构建配置 | 检索配置 |
|---|---|---|
| Cohere / FP32 | [cohere_fp32_build.yaml](cohere_fp32_build.yaml) | [cohere_fp32_recall_bench.yaml](cohere_fp32_recall_bench.yaml) |
| Cohere / FP16 | [cohere_fp16_build.yaml](cohere_fp16_build.yaml) | [cohere_fp16_recall_bench.yaml](cohere_fp16_recall_bench.yaml) |
| GIST / FP32 | [gist_fp32_build.yaml](gist_fp32_build.yaml) | [gist_fp32_recall_bench.yaml](gist_fp32_recall_bench.yaml) |
| GIST / FP16 | [gist_fp16_build.yaml](gist_fp16_build.yaml) | [gist_fp16_recall_bench.yaml](gist_fp16_recall_bench.yaml) |

同一实现支持 1..4096 维的稠密 Cosine / squared L2；维度、M、ef_construction、搜索预算、路由锚点数、投影维度和随机种子都由元数据或配置提供。路由 `ProjectedDimension: 0` 自动选择约半维；Cohere p384 / GIST p256 是已测配置，不是算法内的固定规则。当前仍要求内联向量存储及 AVX-512/VNNI，不能外推为支持任意距离、稀疏或外部向量。

为保留性能，FP32/FP16 的差异在构造索引时选择对应编译期实例；不在每个搜索节点增加通用虚函数或精度判断。加载和路由训练共用同一存储布局校验，统一用物理字节数表达精排预取范围。

## 使用方式

构建使用 `HnswStreamer` 和 `QuantizerName: Fp16Quantizer`，检索配置仍写 `data_type: DT_FP32`，同时增加 `quantizer_param: {"type":"kFP16"}` 和 `use_quantized_graph: true`。这里的 `DT_FP32` 表示接口输入类型；这不是直接传入原生 FP16 数组的接口。

- Cohere：`cohere_fp16_build.yaml`、`cohere_fp16_recall_bench.yaml`。
- GIST：`gist_fp16_build.yaml`、`gist_fp16_recall_bench.yaml`。

将配置中的 `/data` 路径替换为本地路径，然后分别执行：

```bash
./build/bin/local_builder tools/core/bench/cohere_fp16_build.yaml
./build/bin/recall tools/core/bench/cohere_fp16_recall_bench.yaml
./build/bin/bench tools/core/bench/cohere_fp16_recall_bench.yaml

./build/bin/local_builder tools/core/bench/gist_fp16_build.yaml
./build/bin/recall tools/core/bench/gist_fp16_recall_bench.yaml
./build/bin/bench tools/core/bench/gist_fp16_recall_bench.yaml
```

必须使用新的工作文件与 dump 路径，检索打开 dump 文件。FP32 索引不会因切换查询配置而自动转换为 FP16。路由在构建时从数据库训练并写入索引，加载时从索引恢复，不需要外部模型文件。

Cohere 先在 FP32 中归一化，再将坐标舍入为 FP16；不再配置 `CosineFp32Converter`。GIST 保留原始 L2 坐标后转换为 FP16。`fp32_accumulation: true` 控制现有 FP16 量化器的 L2 建图计算；cosine 建图沿用现有量化器内核，不能把该参数解释为所有建图计算均使用 FP32。SymQG 检索精排在两种距离下均显式使用 FP32。

## 数据与计算过程

1. `local_builder` 的每个 worker 按条量化输入，写入原生 FP16 HNSW 存储。量化类型及参数随索引元数据保存。
2. 训练入口树时，按需将抽中的向量展开为 FP32；cosine 训练再做一次归一化，避免 FP16 舍入导致球面聚类的单位范数检查失败。
3. 索引加载时，沿用 SymQG 的边编码和整数中心表示。读取 FP16 原向量时使用临时 FP32 缓冲，不创建常驻全库 FP32 副本。
4. 接口查询保留原始 FP32 值；cosine 在 FP32 中归一化。候选节点进入精排时，先取得并预取一批 FP16 存储句柄，实际评分时才展开所需向量，并使用 FP32 距离累加。预取长度按物理 FP16 字节数计算，避免逐条解码阻塞批量预取，也避免展开在批内已被剪枝的候选。过滤、扩展预算和精确距离扫描预算继续生效。
5. 普通 HNSW、显式暴力检索等其他路径仍遵循其原有量化器语义。本说明中的 FP32 查询精度保证针对 SymQG 检索路径；直接调用底层 streamer 并传入 FP16 查询时，无法恢复已经丢失的 FP32 查询精度。

## 误差与内存边界

设 `x̃ = FP32(FP16(x))`，`e = x̃ - x`。对归一化 FP32 查询 `q`，cosine 的精排分数为 `1 - q·x̃`，其相对未舍入坐标的分数误差满足 `|q·e| ≤ ||e||₂`。存储坐标舍入后范数可能略偏离 1，精排不会再次归一化每条存储向量。

L2 平方距离误差满足：

```text
| ||q-x̃||² - ||q-x||² | ≤ 2 ||q-x|| ||e|| + ||e||²
```

现有整数中心下界基于实际存储值建立，约束的是已展开候选中的终止精排；它既不保证原始 FP32 数据库的排序完全相同，也不保证图导航达到全局精确 TopK。召回仍需对原始 FP32 ground truth 实测。FP16 的取值范围也必须适合输入数据。

百万条向量从 FP32 改为 FP16，坐标字节理论上节省 Cohere 约 1.43 GiB、GIST 约 1.79 GiB。边编码、中心、图邻接表、路由和查询工作区仍存在，不能把这一变化解释为总 RSS 减半。FP16 解码还有计算成本，是否提高 QPS 需要端到端对照。

## 2026-10-30 百万数据验证

使用官方 local_builder 构建新的 FP16 索引，训练路由并 dump，再由官方 recall/bench 加载。对照为原最佳 FP32 SymQG 快照。1000条查询，Top10，原始 FP32 GT；8物理核，ABBA顺序，各版本各线程4个6秒样本，中位数如下：

| 数据集 | 向量存储 | Recall@10 | 单线程 QPS | 8线程 QPS | 8线程搜索 RSS |
|---|---|---:|---:|---:|---:|
| Cohere | FP32 | 90.09% | 50,448 | 403,677 | 7.633 GiB |
| Cohere | FP16 | 90.09% | 49,878 | 401,489 | 6.202 GiB |
| GIST | FP32 | 90.15% | 12,081 | 96,785 | 9.191 GiB |
| GIST | FP16 | 90.16% | 11,855 | 95,051 | 7.403 GiB |

| 数据集 | 单线程 QPS 变化 | 8线程 QPS 变化 | 搜索 RSS 变化 | 主召回不降且两种线程 QPS 损失≤5% |
|---|---:|---:|---:|---|
| Cohere | -1.13% | -0.54% | -18.75% | 通过 |
| GIST | -1.87% | -1.79% | -19.45% | 通过 |

这是相同构建参数下的端到端比较，FP16/FP32 是分别构建的图，并非同图存储格式消融。主查询已参与选参，不属于盲测。RSS来自搜索期间进程采样，未清空page cache。所有计时样本均保留，小幅速度变化不外推到其他机器。

| 参数 | Cohere FP16 | GIST FP16 |
|---|---:|---:|
| M / ef_construction | 50 / 500 | 50 / 500 |
| 路由锚点 / 投影维度 | 65536 / 384 | 8192 / 256 |
| ef_search | 64 | 2048 |
| margin | 0.006125 | 0.086 |
| bucket_width | 0.004 | 0.002 |
| max_expansions | 64 | 256 |
| route_beam / uncertainty_bonus | 1 / 0.15 | 1 / 0 |

初始直接套用 FP32 参数的召回是 Cohere 89.07%、GIST 89.97%，因此必须校准后比较速度。Cohere粗调到90.50%时速度损失超过5%；细调到90.09%并延后FP16解码以保留批量预取后重新完成上述对照。新代码在原FP32索引上的10000个ID/文本分数保持一致；预取调整前后FP16结果也保持一致。

最终103项相关测试通过，另验证不启用RaBitQ的编译路径。两个数据集均完成2048条及百万条索引的构建、训练、dump/load。额外已有Cohere数据库查询（Top10包含自身）的召回为FP32 95.95%、FP16 96.13%，未再据此调参。

本地完整报告与日志：`~/bench/quantized_graph/fp16_symqg_20261030/REPORT_ZH.md`。最终样本和命令位于其`prefetch/`子目录；原始日志、二进制、索引不提交Git。配置关键字段与实际测量YAML已比对，重建索引后仍需复核召回。

## 合并后的通用性与性能回归
